# กรอกเลขพัสดุ BEST ใน FlowAccount

คู่มือนี้สรุปจากงานจริงวันที่ 5 ตุลาคม 2569 ใช้กับการอัปเดตโน้ตของบิลที่มีอยู่แล้ว การติดตั้ง Skill ไม่ใช่คำสั่งให้แก้บิลอัตโนมัติทุกครั้ง ต้องมีคำขอให้ทำงานในรอบนั้น

## ขอบเขตและเครื่องมือ

- อ่านช่วงวันที่จากคำขอ รวมวันเริ่มต้นและวันสิ้นสุด เช่น 28/09/69–05/10/69 คือ 28 กันยายน–5 ตุลาคม 2569 หรือ ค.ศ. 2026 อย่านำช่วงวันที่ตัวอย่างไปใช้เป็นค่าเริ่มต้นของงานใหม่
- ต้นทาง: https://www.best-inc.co.th/my#/orders/from-me
- ปลายทาง: FlowAccount ช่อง **โน้ตภายในบริษัท:** ของบิลที่ผู้ใช้ระบุ งานต้นแบบใช้หน้า **ขายเงินสด / ใบเสร็จรับเงิน (เงินสด)** ไม่ควรอนุมานว่าทุกงานต้องใช้ประเภทเอกสารนี้
- ถ้าผู้ใช้เปิดทั้งสองหน้าไว้ ให้ตรวจแท็บและใช้แท็บเดิม ตรวจบริษัทที่ใช้งานอยู่โดยไม่เดาบริษัทหรือรหัสบัญชีจากงานเก่า
- ใช้เครื่องมือเบราว์เซอร์ที่รองรับใน session และอ่านเอกสาร Computer Use ที่เกี่ยวข้องก่อนใช้งาน ตรวจหน้าเว็บจริงก่อนสร้าง locator; ห้ามใช้รหัสแท็บหรือเลขดัชนีจากรอบก่อน
- เข้าสู่ระบบหรือขอให้ผู้ใช้ช่วยเฉพาะเมื่อจำเป็นตามสถานะจริงของหน้าเว็บ

## 1. เก็บรายการจาก BEST

1. ตรวจชนิดตัวกรองวันที่ งานต้นแบบใช้ **เวลาบุ๊คกิ้ง** หากผู้ใช้ระบุวันรับพัสดุหรือวันจัดส่ง ให้ใช้ความหมายตามคำขอ
2. ตั้งวันเริ่มต้นและวันสิ้นสุด ตรวจค่าที่แสดงหลังเลือก
3. เพิ่มจำนวนรายการต่อหน้าเพื่ออ่านครบ งานต้นแบบมีตัวเลือก 10, 25, 50 รายการ หากจำนวนเกินหนึ่งหน้า ให้เก็บทุกหน้าจนครบตามจำนวนรวม
4. เก็บตารางชั่วคราว: วันที่, ชื่อผู้รับตามต้นฉบับ, เลขพัสดุเป็นข้อความ, สถานะ และรหัสอ้างอิงบุ๊คกิ้งหากจำเป็นต่อการตรวจสอบ
5. แยกรายการสถานะ **ยกเลิกแล้ว** ออกจากชุดที่จะกรอก เว้นแต่ผู้ใช้ขอให้บันทึกรายการยกเลิกด้วย อย่ากรองออกเพียงเพราะยังไม่เซ็นรับ: รายการสร้างสำเร็จ ระหว่างทาง และกำลังนำส่งยังใช้ได้ตามขอบเขตคำขอ
6. ตรวจเลขซ้ำด้วยเลขพัสดุ ห้ามตัดรายการเพราะชื่อผู้รับซ้ำ เพราะหนึ่งบิลอาจมีหลายเลข

## 2. จับคู่กับบิล FlowAccount

1. อ่านบิลทุกหน้าที่ครอบคลุมช่วงวันที่ เก็บวันที่เอกสาร เลขที่เอกสาร ชื่อลูกค้า และยอดรวมสำหรับช่วยตรวจตัวตน งานต้นแบบปรับรายการต่อหน้าเป็น 100
2. เริ่มจับคู่ด้วย **ชื่อผู้รับ + วันที่เอกสาร** การใช้วันที่เดียวกันช่วยแยกลูกค้าที่มีหลายบิล แต่วันบุ๊คกิ้งอาจต่างจากวันบิล จึงไม่ควรตัดสินว่าไม่มีบิลเพียงเพราะวันที่ไม่ตรง
3. ปรับช่องว่างซ้ำและช่องว่างพิเศษเพื่อเปรียบเทียบชื่อ เก็บชื่อเดิมไว้ตรวจสอบ
4. เลขท้ายชื่อ เช่น `ลูกค้าตัวอย่าง ก (1)`, `(2)`, `(3)` อาจหมายถึงหลายกล่องของลูกค้าคนเดียว ถ้ามีบิลที่ตรงเพียงใบเดียวในวันนั้น ให้รวมเลขทั้งหมดในบิลนั้น ไม่ใช่เลือกเฉพาะ `(1)`
5. หากมีหลายบิลของชื่อเดียวกันในวันเดียวกัน ให้ตรวจรายละเอียดบิลและรายละเอียดพัสดุ เช่น ที่อยู่ ผู้ติดต่อ หรือข้อมูลอ้างอิงที่หน้าเว็บแสดง ก่อนแบ่งเลข ห้ามใส่เลขเดียวกันลงทุกบิลโดยไม่มีหลักฐาน
6. ชื่อใกล้เคียงหรือมีคำนำหน้าต่างกันต้องตรวจเป็นรายกรณี งานต้นแบบจับคู่ `คุณ ลูกค้าตัวอย่าง ข` กับ `ลูกค้าตัวอย่าง ข` จากบริบทวันเดียวกัน แต่ไม่ใช่กฎให้ลบคำนำหน้าทุกชื่อ ชื่อ `ชื่อเล่น ลูกค้าตัวอย่าง ค` และ `ลูกค้าตัวอย่าง ค` เป็นคนละรายการ ให้แยกตามหลักฐาน
7. ใช้วันที่ที่แสดงบนบิล ไม่ใช่วันที่ที่อนุมานจากเลขที่เอกสาร งานต้นแบบมีเลขเอกสารขึ้นต้นวันที่ 2 ตุลาคม แต่วันที่บิลแสดง 3 ตุลาคม
8. ทำรายการจับคู่ก่อนแก้ไข: บิล → เลขพัสดุทั้งหมด พร้อมรายการที่ยังจับคู่ไม่ได้ ทำบิลที่ยืนยันได้ต่อไป และถามเฉพาะรายการกำกวมที่ตรวจจากหน้าเว็บแล้วไม่ชัดเจน

## 3. เพิ่มโน้ตและบันทึก

1. เปิดบิลจากเลขที่เอกสาร รอแบบฟอร์มโหลดและชื่อผู้ซื้อปรากฏ ตรวจเลขที่เอกสาร ชื่อลูกค้า และวันที่ก่อนแก้ไข
2. อ่านช่อง **โน้ตภายในบริษัท:** ก่อนเสมอ เก็บข้อความเดิมทั้งหมด อย่าสับสนกับช่อง **หมายเหตุ:** ซึ่งอาจมีข้อความอย่าง `COD`
3. เปรียบเทียบเลขที่ต้องใส่กับเลขที่มีอยู่แล้ว ถ้าครบแล้ว ให้คงไว้และนับเป็น **มีครบอยู่แล้ว** หากขาดบางเลข ให้เพิ่มเฉพาะเลขที่ขาดโดยไม่สร้างเลขซ้ำ
4. รูปแบบที่ใช้ในงานต้นแบบเมื่อเพิ่มข้อความใหม่: `BEST: เลขพัสดุ1, เลขพัสดุ2, เลขพัสดุ3` ถ้ามีข้อความเดิมให้ขึ้นบรรทัดใหม่ก่อนเพิ่ม หากผู้ใช้กำหนดรูปแบบอื่นให้ทำตาม และไม่ต้องเปลี่ยนรูปแบบเลขเดิมที่มีครบแล้ว
5. เปลี่ยนเฉพาะช่องโน้ต ไม่แก้ราคา สินค้า วันที่ลูกค้า สถานะเก็บเงิน หรือช่องหมายเหตุ
6. กด **บันทึกเอกสาร** แล้วตรวจสถานะหลังบันทึก งานต้นแบบปุ่มบันทึกกลับเป็น disabled เมื่อไม่มีการเปลี่ยนแปลงค้างอยู่ แต่ต้องเปิดบิลใหม่เพื่อตรวจการคงอยู่ของข้อมูลด้วย
7. ปิดและเปิดบิลเดิมใหม่ ตรวจโน้ตที่อ่านได้ว่ามีเลขครบและข้อความเดิมยังอยู่ แล้วจึงบันทึกผลว่าเสร็จ หากบันทึกไม่ชัดเจน ให้เปิดอ่านข้อมูลจริงก่อนลองอีกครั้ง เพื่อหลีกเลี่ยงการเพิ่มซ้ำ

### ข้อสังเกตของ UI จากงานจริง

- การคลิกเลขที่เอกสารอาจคืนผลก่อนแบบฟอร์มโหลดเสร็จ ห้ามตีความ snapshot แรกที่ยังแสดงรายการบิลว่าเปิดไม่สำเร็จทันที ให้รอช่องชื่อลูกค้าปรากฏ แล้วอ่านสถานะใหม่
- งานต้นแบบพบ textarea ช่องโน้ตมี `id="note"` และหมายเหตุมี `id="remarks"` ใช้ได้เมื่อได้ตรวจ DOM ในรอบปัจจุบันแล้วเท่านั้น เพราะหน้าเว็บอาจเปลี่ยน
- อย่าใช้ปุ่มเมนูท้ายแถวแทนการเปิดบิลโดยเดา เนื่องจากเมนูอาจแค่เปิด/ปิดหรือถูกสถานะโหลดบัง
- ทำงานเป็นชุดสั้นและรายงานความคืบหน้า ใช้การรอสถานะองค์ประกอบแทนการหน่วงเวลาตายตัว

## 4. ตรวจความครบถ้วนและสรุป

- ตรวจว่าพัสดุที่ไม่ถูกยกเลิกทุกเลขมีบิลที่ยืนยันได้ หรืออยู่ในรายการค้างที่ระบุเหตุผลชัดเจน
- แยกจำนวน **บิลที่เพิ่มหรืออัปเดต**, **บิลที่มีครบอยู่แล้ว**, **เลขพัสดุที่ครอบคลุมทั้งหมด**, **เลขที่ยกเลิก**, และ **รายการค้าง** อย่ารายงานว่ากรอกใหม่ทุกบิลหากบางบิลมีข้อมูลอยู่ก่อน
- ทุกบิลที่นับว่าเสร็จต้องเปิดอ่านหลังบันทึกหรือยืนยันว่ามีครบอยู่แล้ว ข้อมูลที่ยังอยู่ในแบบฟอร์มก่อนกดบันทึกไม่ถือว่าเสร็จ
- เก็บภาพตัวอย่างบิลที่เห็นเลขที่เอกสารและช่องโน้ตหลังเปิดใหม่ ให้ผู้ใช้ตรวจได้ หากมีภาพ ให้แสดงแบบ inline ในคำตอบ
- สรุปภาษาไทยกระชับ ระบุช่วงวันที่ จำนวน และรายการค้างถ้ามี ไม่เปิดเผยรายชื่อและรายละเอียดส่วนตัวทั้งหมดโดยไม่จำเป็น

## ผลของงานต้นแบบ

ช่วง 28 กันยายน–5 ตุลาคม 2569: พบ 42 รายการใน BEST, ยกเลิก 3 รายการ, ครอบคลุม 39 เลขใน 29 บิล เพิ่มหรืออัปเดต 20 บิล และอีก 9 บิลมีเลขครบอยู่แล้ว ไม่มีเลขที่จับคู่ค้าง ผลนี้เป็นตัวอย่างการนับเท่านั้น ไม่ใช่ข้อมูลสำหรับกรอกซ้ำในรอบใหม่


## การใช้ใน Codex Cloud

Skill นี้มีขั้นตอนทำงาน แต่ไม่มีข้อมูลเข้าสู่ระบบหรือเครื่องมือเบราว์เซอร์รวมอยู่ด้วย ก่อนแก้บิลใน Cloud ให้ตรวจว่า session มีเครื่องมือเบราว์เซอร์ที่รองรับและเข้าสู่ระบบทั้งสองบริการได้จริง หากไม่มี ให้รายงานข้อจำกัดและใช้ Codex บนเครื่องที่เชื่อมเบราว์เซอร์ได้ ห้ามรายงานว่ากรอกข้อมูลสำเร็จจากการอ่านคู่มือเพียงอย่างเดียว
